# Native T3 Code integration

Minecraft is the window. Your paired T3 machine is the authority. This guide maps that connection and separates checks we actually ran from work still waiting for a live machine or another operating system.

The inspected MCP endpoint accepts live provider-session credentials. Those are unsuitable as a durable independent Minecraft login. T3Craft uses T3's paired-client auth and native HTTP/RPC routes instead. This reaches the user's existing conversations directly while allowing T3's agents to continue using the app-owned MCP tools.

Its separate office, server, world-control MCP and automation features were excluded. [Attribution](../THIRD-PARTY-NOTICES.md) and its license ship in the JAR.

## Architecture

Workflow navigation derives its next action from the owning machine's health, current pending requests and fetched ready checkpoints. The work inbox, chat header and resident controls share `T3Workflow`; they do not create execution state. Setup progress and remembered chat filters are local UI preferences. Resident review poses come from actual ready checkpoints, while command-watching poses require a receipt from the active run. Only two request owners approach the player; additional waiting residents remain at their assigned desks. Pending approvals lock until the exact request is acknowledged or fails, and prepared message retries retain their original model and delivery mode.

Resident typing, mouse pauses, head gestures and nearby thought expressions are derived cosmetic animation. Per-resident timing avoids synchronized hand movement; detected seat/desk geometry places a keyboard and mouse without world writes. Pending requests and machine health take priority over remembered activity. Completion smiles share the existing live-transition guard, so loaded history does not celebrate. Speech remains actual newly completed T3 replies and takes visual priority over thought expressions.

Residents also greet a nearby player, stretch while seated and idle, shift their weight while waiting, point during review and lean while watching commands/tests. Settled residents take staggered lounge breaks with small snack, phone and relaxed developer-idle gestures; these are cosmetic and do not change T3 state. Newly generated modern HQs have eighteen work anchors on the main daylight floor. In older authored saves, `StationAssigner` projects upstairs work assignments onto distinct existing main-floor meeting and lounge seats; it preserves the saved blocks and anchor file. Settled threads retain lounge destinations. These gestures preserve current activity and seat; walking, failures, pending requests, paused work and offline state retain their priority. Client-only walkers check swept body clearance before consuming a path segment. Shared destinations reserve separate positions, and crowded walkers yield, try a checked sidestep, then a retreat around the group. All detour segments must clear both the saved world's floor geometry and other residents. Sealed routes hold on safe ground until space opens.

```mermaid
flowchart LR
  HQ["Minecraft studio, NPCs and stations"] <--> Client["Native Java T3 client"]
  Client <-->|"Paired HTTP + ticketed WebSocket"| T3["T3 Code environment"]
  T3 <--> Runtime["Existing chats, providers and workspaces"]
  T3 <--> MCP["App-owned MCP tools for agents"]
```

There is no Node bridge, Foreman runtime, embedded Claude SDK or simulated-chat source. The retained studio snapshot structures are an internal rendering projection of T3 state; they do not perform orchestration.

## Compatibility and release policy

The supported Minecraft target remains 26.3 with Fabric; this change prepares additional targets without claiming support for Minecraft 1.21.x, NeoForge or an untested future version. `mod/gradle.properties` owns the build versions and Java minimum. Resource processing derives the mod's exact Minecraft requirement and minimum Fabric Loader/API/Java requirements from it. The release packager verifies those declarations against the compiled JAR and emits `compatibility.json`, version-labeled archives, a stable Prism ZIP and SHA-256 checksums. Unexpected files, private game/config data, local Java paths and mismatched targets are rejected before release packaging succeeds.

Build/release CI compile, validate the portable package and check paired protocols 1/2 on Windows, macOS and Linux. Windows additionally runs installation/update checks in disposable synthetic profiles. Runtime support and evidence remain separate: CI does not establish native macOS/Linux gameplay, every shader combination, real remote writes or external Git/PR hosts. Add a new Minecraft target only after its Fabric versions, Java requirement, Minecraft hooks, mixins, world recovery and game surfaces are built and checked; older mapped releases may require a separate Loom/source adaptation. Keep T3 wire parsing in `T3Api`/`T3Protocol` and game integration at the client hooks rather than copying workflow logic for each target.

New players import a prebuilt Prism ZIP. The optional Windows release installer verifies the bundled or downloaded package, backs up all saves/mods/config before updating an exact matching Minecraft/Fabric profile, and retains credentials and player settings. First unpaired world entry offers Connections once per session; successful first pairing continues to the existing guide and executes no T3 work. Routine mod updates do not queue a campus rebuild. Development launches resolve the installed native Prism world, while fixture QA explicitly overrides both game directory and pairing config.

The release includes the clean authored save in `release/world-template.zip`, with source-save provenance and file hashes in its adjacent manifest. The explicit closed-world exporter retains authored blocks, signs, terrain, anchors and the saved building plan; player files, entities, inventories, profiles, scheduled events and personal configuration are excluded. Fresh imports load that saved world without regenerating the campus. Existing-instance updates install only managed mods. `--verify-world-source` detects changes after capture, and CI validates the pinned snapshot independently of the author's machine.

## Authentication and history

Pairing exchanges a one-time environment-bootstrap link for a client credential scoped to `orchestration:read orchestration:operate`, plus `terminal:operate review:write` on protocol 2. These additional scopes enable the implemented shell and review RPCs; the issuing grant remains authoritative. Earlier credentials cannot gain scopes automatically: create a fresh link in T3 Settings → Connections and pair the same machine again. The credential is saved in Minecraft's private `config/t3craft.json`. Windows ACLs restrict the configuration to its owner; replacement is atomic. The installer issues a new authorized pairing grant through the installed T3 CLI instead of extracting an existing app session.

The client checks public environment metadata, sends `x-t3-orchestration-protocol: 2`, loads the shell and selected bounded thread projection, and subscribes through a one-time WebSocket ticket. Long-lived access credentials do not appear in socket URLs.

Older history loads through the opaque cursor from the bounded projection and subsequent history pages. History and archived conversations are available through Workspace. Unsent drafts, terminal input and stable chat retry commands live in the private configuration; saved conversation history remains owned by T3. No raw provider transcript directories are consulted.

Protocol 1 compatibility paths are retained from the adapted client and covered by fixtures separately; protocol 2 is the live verified target. T3's rapidly changing client RPC surface is not a guarantee of compatibility with future versions.

The client negotiates the environment's advertised orchestration protocol before pairing and includes that version on authenticated HTTP requests. Optional attachment APIs are capability-gated from the same public environment descriptor: uploads must be advertised, file uploads additionally require `fileAttachments.maxUploadBytes`, and the full draft is checked against those limits before any file is uploaded. This matters during T3's V1-to-V2 transition: a V1 client and V2 server (or the reverse) reject each other, so update every connected T3 environment when changing protocol generations. Missing optional capability fields mean unsupported; the client keeps the draft and reports which machine needs updating.
